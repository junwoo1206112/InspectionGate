# 교차 검증 결론

## 서로 독립적으로 일치한 결론

1. **모델 출력을 최종 결정으로 취급하지 않는다.** CV 관점에서는 확률의 과도한 해석을 피해야 하고, 제품 관점에서는 HOLD와 검토 이력이 필요하다.
2. **HOLD 유형을 구분한다.** 저점수는 사람이 사유를 남긴 뒤 최종 결정을 할 수 있지만, 입력 품질 실패는 이미지 교체·새 예측이 필요하다.
3. **재현 근거와 성능 근거를 분리한다.** ONNX/API/Docker는 실행 재현성, 누수 방지 split과 교란 표는 평가의 신뢰성을 보여 준다.

## 충돌과 해결

| 긴장 관계 | 해결 |
| --- | --- |
| 사람이 최종 결정할 수 있어야 함 vs 품질 불량 이미지를 억지로 확정하면 안 됨 | `HOLD_INPUT_QUALITY`는 review endpoint가 거절하고 새 `prediction_id`만 생성 가능하게 한다. |
| 점수를 보여 주고 싶음 vs 신뢰도라고 과장할 위험 | `max probability`로 표기하고 calibration 검증 전에는 신뢰도/안전 보장을 주장하지 않는다. |
| 빠른 데모 vs 재현 가능한 증거 | 코드와 별도로 manifest·결과 JSON·smoke test를 artifact로 남긴다. |

## 채택한 권장안

로컬 단일 검토자, 저장 이미지, JSONL 감사 이력, 명시적 HOLD 상태 머신을 최소 제품으로 구현한다. 실제 모델·공개 데이터 평가는 별도 phase에서 붙이며 수치는 실행 후에만 기록한다.
